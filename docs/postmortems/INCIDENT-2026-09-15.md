# Incident: a saturated database collapsed request capacity, dropping ~1M requests over ~5.5 hours on 2026-09-15

## What happened

On 2026-09-15, a partner script made a request to the v1 API's single-form
endpoint, requesting embedded submissions for one form at the maximum permitted
page size over a roughly 30-day date range. The request was slow — slow enough
that it never completed within the caller's patience.

The request ran for roughly 120 seconds, at which point the calling script timed
out and disconnected. The gateway logged a 499 — nginx's code for "client closed
request." The script treated the timeout as a failure and retried, then continued
retrying every 2–3 minutes for several hours, roughly 130 attempts in total.
Every one of its requests is logged as a 499, so no attempt ever completed inside
the 120 seconds available to it.

The 120-second limit is the caller's, not ours. Confirmed with the script owner:
the script runs in Microsoft Power Automate, whose documented request timeout
produced the cutoff
([limits and configuration](https://learn.microsoft.com/en-us/power-automate/limits-and-config#timeout)).
It is a property of their platform, so it is neither something we set nor
something they can raise.

Each retry started a new copy of the same expensive query. **Critically, the
disconnect terminated only the client connection — Rails is never notified that
a caller has gone away mid-request, so the Postgres queries continued executing
server-side.** Each retry therefore added its cost on top of work that was still
running. By the time of recovery, several queries had been running for over an
hour.

Nothing we configure would have stopped them. There is no `rack-timeout` or
equivalent in `../../Gemfile.lock`; Puma has no request-timeout mechanism and
`../../config/puma.rb` sets only `threads` and `port`; no `statement_timeout` is
configured. The platform imposes limits we do not control — cloud.gov's router
has a request timeout, and its brokered Postgres may have its own — but whatever
their values, they did not contain this incident.

The distinction that matters is not whether some timeout exists somewhere. It is
that *the connection closing and the query stopping are unrelated events*. Even
if the router had severed the connection at some point, the query behind it
would have continued exactly as it did at 120 seconds.

Recovery required two manual actions: asking the partner to stop the script, and
manually cancelling the queries still running. The system recovered immediately
afterward.

Duration: onset ~11:50am ET, recovery ~5:24pm ET. Roughly 5.5 hours.

## What was saturated

**The database.** A 1-core instance (cloud.gov plan: "Single-AZ RDS instance of
PostgreSQL, minimum 1 core, minimum 8 GiB memory") cannot absorb several
concurrent copies of an expensive query, and once saturated it slows *every*
query on the platform. Thread exhaustion followed from that.

Measured, from New Relic and the Cloud.gov logs:

|                                                        | Normal          | During window                 |
|--------------------------------------------------------|-----------------|-------------------------------|
| Median database request time                           | ~0.01s          | **~1s**                       |
| Median web request execution time, DB-touching request | —               | ~1.1s                         |
| Average web request execution time, all requests       | 30ms             | 540ms                         |
| p95 / p99 response time                                | ~100ms (p95)    | 1500ms / 1800ms               |
| Throughput                                             | ~12,000 req/min | **~6,000 req/min**            |
| Database CPU                                           | ~40%            | 100%, sustained               |
| Database connections                                   | ~55             | 74 (of `max_connections` 830) |
| App 499s                                               | —               | **~1,000,000**                |
| App 502/504s                                           | —               | none                          |

The chain these numbers describe:

1. A few concurrent expensive queries saturate the database's single core.
2. Every database query slows by roughly **100×** — 0.01s to ~1s. This is the
   measured root cause, not an inference.
3. Mean web service time therefore inflates roughly **18×**, from ~30ms to
   ~540ms, since most of a typical request is database time.
4. Fleet request capacity is `54 threads ÷ avg request time`. At ~30ms that is
   ~1,800 req/s; at ~540ms it is ~100 req/s. (54 threads comes from 18 app instances running 3 threads each.)
5. Demand stayed at ~200 req/s. Capacity fell to roughly half of it.
6. Requests queued waiting for a Puma thread. Clients abandoned them.

Two caveats on the numbers above:

- **Recorded latencies are survivor-only.** New Relic measures transactions that
  completed. The ~1M requests clients abandoned never entered any percentile, so
  p99 = 1800ms is the worst case *among survivors*, not the worst case.
- **Why 100× rather than ~10×.** CPU contention on 1–2 cores accounts for
  perhaps an order of magnitude. The excess is plausibly buffer-cache eviction:
  the query scans large numbers of wide, TOASTed rows, displacing the working
  set that normally serves ordinary queries from memory, and the external-merge
  sorts competed for the same disk. This is a hypothesis, not a finding, and it
  matters for remediation — cache thrash is fixed by more memory, CPU contention
  by more cores.

Three resources were *not* saturated, recorded to stop them being
re-investigated:

- **Database connections.** 74 against `max_connections` 830 — roughly 9%. A
  blocked request occupies a connection its thread already held rather than
  adding one, so connection count could never have measured the problem.
- **Thread capacity in the normal case.** At ~12,000 req/min and ~30ms service
  time, the 54 threads run at roughly **11% utilization**. Headroom was healthy;
  an 18× service-time inflation would overwhelm any reasonable thread count.
- **Platform stability.** `cf events` shows no crashes, restarts, deploys,
  scaling changes, or task containers during the window.

## Impact

**Approximately 1 million requests were abandoned by clients over 5.5 hours**,
and requests that were served took roughly 18× longer than normal — average
execution time rose from ~30ms to ~540ms. This was a
public-facing partial outage, not an internal slowdown: Touchpoints serves
embedded feedback widgets on other agencies' sites, so a hanging response means
a broken widget on a third-party page and a visitor who navigates away.

The gateway logged no 502s or 504s, so every loss was a client giving up rather
than the router timing out. That is itself a finding: **the router's timeout is
longer than user patience, so it provided no effective bound.** Nothing in the
stack capped the wait, just as nothing cancelled the work.

1.7K of the abandoned requests were POST requests, which includes failed survey submissions as well as 
failed edits by Touchpoints users. This represents lost potential survey feedback and frustrated users but there should
be no data integrity implications.

Detected via user report. **No alert fired**, despite ~1M failed requests, a 50%
throughput drop, and sustained 100% database CPU. Alerting is tracked
separately, but see follow-ups for the two metrics that would have detected this
within minutes.

A diagnostic hazard worth recording: the partner's ~130 retries and the ~1M
collateral abandonments produced **the same status code**. Anyone triaging by
499 volume saw a sea of them with the causal signal at roughly 1 in 10,000,
visible only by filtering on the API path or key. That is part of why this took
5.5 hours and a user report to identify.

## Why this became an outage rather than one failed request

**The slow query was the trigger, not the cause.** A single expensive request
should produce a single failed request. What turned it into 5.5 hours of
platform-wide failure is that the system had no mechanism to stop, bound, or
shed abandoned work. Any query capable of saturating the database would have
produced the same outcome, so making this particular query faster raises the
threshold without removing the failure mode.

1. **A client disconnect does not cancel the query, and nothing we control
   bounds it.** A disconnect frees the gateway, but Rails never learns the
   caller is gone: the Puma thread stays blocked on the Postgres socket until
   the query returns, holding both the thread and its connection from the pool.
   With no `statement_timeout` in `../../config/database.yml` and no
   request-level timeout in the application, an abandoned query runs to
   completion — here, over an hour, confirmed by recovery requiring manual
   cancellation.

   This is the mechanism that made retries *additive rather than idempotent*,
   and it is the most important finding in this incident. A retry of a failed
   request should cost what the first attempt cost. Here each retry added its
   cost on top of work that was still running, while the caller believed it was
   simply trying again.

   Note that a request-level timeout alone would **not** have been sufficient.
   It frees the Puma thread but does not reach the database, so the query keeps
   running and the database stays saturated — meaning every other request stays
   slow and the outage continues. Only a `statement_timeout` stops the work
   itself. The two bounds are not interchangeable and are ranked accordingly
   below.

2. **Request capacity collapsed because service time inflated, and nothing
   shed load.** `RAILS_MAX_THREADS` is unset in production, so defaults apply:
   `../../config/puma.rb:29` gives 3 threads per instance, and with 18 web
   instances the fleet can serve at most 54 concurrent requests.

   That is normally ample — roughly 11% utilized. But thread capacity in
   requests-per-second is `54 ÷ service time`, so an 18× service-time inflation
   divides it by 18. The fleet did not lose threads so much as lose throughput
   per thread, and no mechanism existed either to reclaim threads held by
   abandoned work or to shed arriving load once capacity fell below demand.

   Note that database pool capacity was never the binding resource. `pool` is 5
   per process (`../../config/database.yml:22`) against 3 threads, so checkout
   can never block and `ActiveRecord::ConnectionTimeoutError` is unreachable in
   this configuration.

3. **Rate limiting existed but measured the wrong thing.** The API gateway
   enforces 1000 requests per hour per key. The script's retries every 2–3
   minutes amount to roughly 20–30 requests per hour, so it ran at a few percent
   of its allowance and the limit was never approached. Within the application
   there is no throttle at all on the API namespace:
   `../../config/initializers/rack_attack.rb` covers only form submission POSTs,
   and is keyed on IP rather than API key.

   A request-count limit is the wrong instrument when an abandoned request keeps
   consuming resources (gap 1). Under those conditions 1000 requests per hour
   permits an essentially unlimited amount of *concurrent* work — and
   concurrency against a 1-core database is precisely the quantity that caused
   the damage. The script's own request volume was statistically invisible:
   ~24/hour against ~720,000/hour platform-wide. It mattered only for what it
   did to a shared database.

### Why this is not a publicly available security flaw
Access to the affected endpoint requires HTTP basic auth plus a valid API key
resolving to a user with access to the form in question, so the incident was
reachable only by already-credentialed callers.

## Remediation

Ordered by how much each reduces blast radius. The first item is in a tier of
its own: it is the only control that stops the database saturation that caused
the outage.

- [ ] **Set a `statement_timeout` for the API path.** The single highest-value
      change. It bounds the work itself rather than the waiting for it, and it
      is the only bound that lives below the application — it holds even if the
      request, the thread, or the whole process goes away.

      Choose the value from what API endpoints legitimately need, and choose it
      aggressively: on a 1-core instance a *single* query of this cost degrades
      the entire platform, so there is no safe level of concurrency to tune
      around. The caller's 120 seconds is a useful *upper* bound — a query
      outliving the only connection waiting for it is pure waste — but it is a
      ceiling, not a target, and it belongs to one caller's platform rather
      than to our infrastructure.

      Note that `../../config/database.yml` can only set this globally for
      every connection in the pool — it cannot be scoped to the API path. A
      path-scoped timeout requires either `SET LOCAL statement_timeout` in
      `../../app/controllers/api_controller.rb` (per-request, and only takes
      effect inside a transaction) or a separate database role and pool for API
      traffic. These differ in risk and effort; the implementing ticket should
      choose one explicitly rather than leaving it to the implementer.
- [ ] **Limit concurrent in-flight API requests per key.** The damage scaled
      with the number of expensive queries running simultaneously against one
      core, and this is the control that bounds exactly that quantity. The
      gateway's 1000/hour cap did not engage — the script used a few percent of
      it — because request count was never the relevant measure.

      Implementable in Rack::Attack, though note that
      `../../config/initializers/rack_attack.rb` currently covers only form
      submission POSTs and is keyed on IP, so the API namespace needs a new
      rule keyed on API key. Size it low: a single key should not be able to run
      more than a small number of concurrent requests against a single-core
      database.

      The cap must be enforced through the shared Redis store rather than
      per-instance memory. `rack_attack.rb:3-7` prefers Redis when `REDIS_URL`
      is set but falls back to per-instance `Rails.cache` otherwise; with 18
      instances that fallback would make any cap effectively 18× looser than
      configured. `REDIS_URL` is set from `VCAP_SERVICES` by
      `../../config/initializers/vcap_services.rb`, so this should hold in
      production — confirm rather than assume, since the fallback fails
      silently.

      A per-key request-rate throttle is still worth adding as a cheap
      secondary guard against pathological retry loops, but it should be
      understood as defense in depth.
- [ ] **Add a server-side request timeout.** Secondary to the two items above:
      it bounds thread occupancy but does not stop the query, so on its own it
      would not have contained this incident — the database would have stayed
      saturated and every request would have stayed slow. It is still worth
      having, because it caps thread hold time, turns an indefinite hang into a
      legible failure, and bounds time spent outside the database that a
      `statement_timeout` cannot reach.

      Currently missing from everything we configure: no `rack-timeout` or
      equivalent is in `../../Gemfile.lock`, Puma offers no request timeout, and
      `../../config/puma.rb` sets only `threads` and `port`.

      cloud.gov's router imposes its own request timeout, but it is demonstrably
      longer than users are willing to wait — ~1M clients abandoned before it
      fired — so it provides no useful bound. An application-level timeout we
      own is configurable per-endpoint, observable in our logs, and testable.
- [ ] **Review database sizing.** One core is the resource that actually
      saturated, and nothing else on this list changes it. Before sizing,
      resolve whether the 100× query slowdown was CPU contention or buffer-cache
      eviction (see "What was saturated"), because the two call for different
      changes — more cores versus more memory. The cloud.gov plan description
      ("minimum 1 core, minimum 8 GiB") does not state what is actually
      provisioned, so establish that first.
- [ ] **Return a structured error instead of hanging.** Once a timeout exists,
      the response it produces should be actionable: a prompt 4xx/5xx naming
      what to change beats a silent stall. A two-minute hang reads as a
      transient failure, which is what invites retries in the first place.
- [ ] **Work with the partner on retry behavior** — backoff, and a cap on
      consecutive retries. Unlike the other items this one is part of the
      trigger, not just a mitigation: the script's timeout-and-retry loop is
      what sustained the load for 5.5 hours. It ranks last because every
      server-side item above must hold without any client cooperation, and
      because the 120-second timeout is imposed by Power Automate and cannot be
      raised — so this caller cannot fix the problem from their end even if
      willing.

      Worth confirming the loop's actual structure before writing this ticket.
      Power Automate's built-in HTTP retry policy is 4 attempts with
      exponential backoff, which cannot produce retries every 2–3 minutes for
      5.5 hours. The loop is more likely a scheduled flow or an explicit
      Do-Until, in which case "add backoff" is the wrong ask and a concurrency
      guard or longer recurrence interval is the right one.

## Follow-up for future diagnosis

- [ ] **Alert on request queueing time.** New Relic was recording it throughout
      the incident and it was the metric that identified the saturated resource
      after the fact. It goes non-zero only when thread capacity is the
      constraint, so it has few false positives, and it would have fired within
      minutes of onset. Highest-value item here.
- [ ] **Alert on throughput deficit** — a sustained drop against the expected
      baseline for the time of day. Throughput halved for 5.5 hours and nothing
      noticed; this is the signal that distinguishes "slow" from "not serving."
